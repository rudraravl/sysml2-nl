Example 1 NL:
This model describes a vehicle and trailer towing system. The system consists of three main components: a vehicle, a trailer, and a separate trailer hitch assembly that connects them.

The trailer hitch assembly is the central connecting element and is composed of two key parts: a hitch ball and a trailer coupler.

In this configuration, the vehicle itself does not own the hitch ball, but is set up to interface with the one provided by the hitch assembly. Similarly, the trailer connects to the trailer coupler, which is also part of that same hitch assembly.

Essentially, the system shows a vehicle and a trailer being joined together by a common, self-contained hitch mechanism.

Example 2 NL:
This describes the automated process of a digital camera system for taking a photograph. The system is designed to capture a real-world scene, process it, and display the final result.

The process begins when a user aims the camera at a "scene." The system's first step is to "focus," which adjusts the optics to create a sharp, clear "image" on the camera's sensor. Immediately following this, the "shoot" action captures this focused image, converting it into a final digital "picture." As the final step, this newly created picture is sent to be displayed on a "screen," providing immediate visual feedback to the user.

Example 2 SysML:
package 'Messaging Example' {
	item def Scene;
	item def Image;
	item def Picture;
	attribute def Show {
		item picture : Picture;
	}
	action def Focus { in item scene : Scene; out item image : Image; }
	action def Shoot { in item image : Image; out item picture : Picture; }
	action def TakePicture;
	action screen;
	action takePicture : TakePicture {
		action trigger accept scene : Scene;
		then action focus : Focus {
			in item scene = trigger.scene;
			out item image;
		}
		flow from focus.image to shoot.image;
		then action shoot : Shoot {
			in item image; 
			out item picture;
		}
		then send new Show(shoot.picture) to screen;
	}
}

Example 3 NL:
This model describes the architecture of a multi-layered software application. It is designed with a classic three-tier structure to separate user interaction, business logic, and data storage.

The system includes an **Application Layer**, which is the part the user interacts with, like a graphical user interface or a web page. Beneath that is a **Service Layer**, which contains the core logic and rules of the application. It processes user requests and performs the main functions of the software. Finally, there is a **Data Layer** responsible for storing and retrieving all the application's information, essentially acting as its memory or database.

The layers are organized so that the Application Layer communicates its requests to the Service Layer, which in turn interacts with the Data Layer to get or save information. The system also handles data calculations where a final value depends on other inputs. For instance, a result 'z' is computed based on two other input values, 'x' and 'y'.

Example 3 SysML:
package '12a-Dependency' {
	package 'Application Layer';
	package 'Service Layer';
	package 'Data Layer';
	dependency Use from 'Application Layer' to 'Service Layer';
	dependency from 'Service Layer' to 'Data Layer';
	attribute x;
	attribute y;
	attribute z;
	dependency z to x, y;
}

Example 5 NL:
This model describes a digital camera system designed to capture and display photographs. The system consists of two main components: the camera body and a display screen.

The camera's primary function is to take a picture, which is a three-step process. First, the user aims the camera's lens (the viewport) at a real-world scene. The camera then automatically focuses on that scene to create a sharp, internal optical image. Once the picture has been created, the camera body sends it to the attached screen, which then displays the newly taken photograph for the user to review.

System models are expressed in KerML using a textual concrete syntax. This can be parsed to an abstract syntax
representation, which is then given a semantic interpretation for the system being modeled. The semantics for the
KerML core constructs is grounded in formal mathematical logic, providing a consistent basis for mathematical
reasoning about KerML models. However, beyond this, the semantics of KerML constructs are specified by the
relationship of user model elements to the KerML Semantic Library.
The Semantic Library models, also expressed in KerML, provide an ontological model of the meaning of KerML
models. Indeed, all KerML models can be semantically expressed using solely core modeling constructs referencing
the appropriate semantic concepts defined in the Semantic Library. KerML semantic constructs beyond the core are
essentially just syntactic conveniences for reusing specific library concepts: structures for modeling objects,
behaviors for modeling performances, associations for modeling links, etc.
Indeed, the full KerML language can be considered to be simply a syntactic extension of the core, which is
semantically extended using library models. By intent, this approach can also be used to build on KerML to create
more specific modeling languages. Application specific modeling languages can be built on KerML by extending
the KerML abstract syntax, specializing its semantics, with concrete syntaxes similar to or entirely different from
KerML's.
